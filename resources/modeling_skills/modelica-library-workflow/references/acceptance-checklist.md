# 验收清单

## 完成口径

以下四类是实际证据层级，不能互相替代。先按用户请求确定终点，再验收该范围；后续阶段未请求时记 `not_required`，已要求但未执行记 `blocked`（说明未执行原因），证据不足记 `blocked`（说明证据缺口）。不得把“尚未达到运行级”写成“骨架或文件任务未完成”。

| 完成层级 | 最低证据 | 不代表 |
| --- | --- | --- |
| `plan-complete` | 任务边界、结构方案或评审发现、依据与必要假设已交付 | 已修改文件或已在工具中验证 |
| `files-modified` | 请求文件实际落地，改动可追溯，命名/引用/目录基本一致 | 顶层已加载、示例能运行 |
| `structure-level-verified` | 对实际请求对象完成可复核的静态结构与引用检查；模板规则仅在采用模板时适用 | 已通过工具 check / translate / simulate |
| `run-level-verified` | 请求模型真实仿真成功，且已要求的前置检查和结果验收有证据 | 未触及模型或额外指标也已通过 |

## 方案、文件与结构验收

1. 方案或只读评审无需真实文件修改；发现问题不授权自动修复。
2. 生成骨架只验收请求的骨架、`package.mo` / `package.order` 与引用；不强制创建可运行 Examples / Tests，不启动 Sysplorer。
3. 文件任务可在静态检查后完成，不把加载、检查、翻译和运行混入“文件已修改”的定义。
4. 采用模板时核对其公共层、接口族与展示顺序；其他工程核对现有设计的兼容性和一致性，不强制套用模板。
5. 纯 Documentation、本地化或未改变图形对象的任务，图面状态按父级 Gate 6 记 `not_required`。新建或实际修改图形对象只验收涉及层级；自动布局改动也计入。
6. 静态结构检查不能冒充目视验收。图面证据与最终完成条件统一服从父级 Gate 6。

## 工具阶段与可运行验收

- “可加载”需真实加载/打开证据；“check 通过”需对应检查证据；“translate 通过”需对应翻译证据。逐项报告，不把其中任一项升级为运行级。
- 用户要求可运行库或首版可用时，顶层库和约定的首个 Examples / Tests 入口须有真实证据；只请求一个可运行示例时验收该示例，不自动增加测试任务。
- 仅 simulate 成功的任务不追加结果读取；只有明确结果验收、KPI 分析或异常诊断才读取必要变量。失败的本轮仿真不能由旧结果改判成功。
- 仿真与图面分别列状态；视觉问题不阻塞工具执行，完整图形交付仍须适用 Gate 6 通过。
- 当前环境未执行要求的工具阶段时，交付已经完成的文件/结构事实并列明剩余项；不能写“可运行”或用 `not_required` 掩盖已请求验证。

## 交付前核对

- 完成声明与实际请求、实际证据一致。
- 示例、测试、图面、结果及文档各项只评价本轮适用范围。
- 未运行项、真实失败与纯范围外项明确区分。
- 独立文档/报告仅在请求时生成；必要类说明、参数说明与维护既有引用属于实际模型修改。
- Skill 发布检查另见 `promotion-checklist.md`；静态适配完成不代表真实触发或新版 MCP 回归通过。
