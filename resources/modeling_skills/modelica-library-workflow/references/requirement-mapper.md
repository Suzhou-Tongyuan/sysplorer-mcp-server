# 任务识别与分流

## 角色

本文档只负责一件事：把用户的自然语言请求快速映射成 **模型库任务类型、当前缺口和默认起步动作**。

它不负责重复定义 package 规则、接口硬约束或交付口径；这些内容分别交给 `template-package-scheme.md`、`executor-base.md`、`workflow-checklist.md` 和 `input-output-contract.md`。

## 一级分流：先定主任务

先判断目标是否涉及库结构、公共接口、Examples / Tests、库级本地化或治理。普通单模型的建模、修复、评审、文案和导图不触发本 Skill。已有具体故障由父级独立调试入口主导；仅在故障涉及库结构/公共接口时提供本地支持，不重新启动建库流程。

收到请求后，先只选一个主任务类型：

1. 从 0 到 1 建库
2. 沿模板整理模型库
3. 扩展已有模型库
4. 评审已有模型库
5. 中文化 / 本地化修订
6. 图面与连线修复
7. 模型库 + 首个示例/测试验证

若一个请求同时包含多个目标，先判断 **本轮最主要的交付对象**：

- 若主要目标是“形成库结构”，归入建库或整理。
- 若主要目标是“补一个新组件/新业务包”，归入扩展。
- 若主要目标是“判断现状哪里不对”，归入评审。
- 若主要目标是“给出首版可用、已验证示例”，归入“模型库 + 首个示例/测试验证”。
- 若主要目标已经转成物理建模、多工况仿真、参数调整或控制分析，则库 workflow 只保留结构和交付职责，建模主循环应交回父 skill 或领域 skill。

## 任务类型映射

| 用户意图 | 默认任务类型 | 起步动作 | 首轮重点产物 |
| --- | --- | --- | --- |
| “按流程建一个模型库” | 从 0 到 1 建库 | 先定请求终点、领域边界、顶层 package 和正式库名 | 约定的骨架/文件/结构或可运行交付，不默认运行 |
| “参考模板整理这个库” | 沿模板整理模型库 | 先比对模板结构与当前结构差异 | 差异清单、归位方案、重命名方案 |
| “给这个库补组件/接口/示例/测试” | 扩展已有模型库 | 先查现有分层和可扩展位置 | 新增位置、影响范围、最小验证范围 |
| “帮我评审一下这个库” | 评审已有模型库 | 先按检查清单找缺口和错位 | 发现列表、风险、修补顺序 |
| “把库内说明改成中文” | 库级中文化修订 | 先区分标识符、显示名、文档说明 | 中文化范围、兼容性风险 |
| “整理库内公共接口/组件族的图面” | 库级图面与连线修复 | 先查 `connect(...)` 是否缺 `annotation(Line(...))`，再查 `Placement` / `Diagram` | 图面修复点、影响范围、复核点 |
| “建一个模型库并给可运行示例 / 测试” | 模型库 + 首个示例/测试验证 | 先定顶层库、首批业务包和用户要求的示例/测试 | 约定入口的真实验证状态；仅要示例不追加测试套件 |

## 最小输入集

理想情况下，先确认以下信息：

1. 目标领域：液压、热液压、气动、机械、电气、控制或跨域
2. 当前对象：模板库、已有库、表示库/公共接口的 `.mo` 文件或库流程说明；文件数量不单独决定任务归属
3. 本轮目标：建库、整理、扩展、评审、中文化、图面修复或示例验证
4. 交付粒度：方案、真实文件修改、最小案例、首版可用库
5. 工具链：MWORKS / Sysplorer、Dymola、OpenModelica 或混合兼容
6. 语言要求：仅中文化用户可见内容，还是连标识符一起处理

## 缺失输入时的默认补足

| 缺失项 | 默认补足策略 |
| --- | --- |
| 未给模板 | 先按通用顶层结构规划 |
| 未给正式包名 | 先给正式命名建议，不保留占位名 |
| 未给交付粒度 | 依据原请求执行：要求建库则落所需文件并静态检查，只要建议则交付方案；不擅自追加运行 |
| 未给中文化范围 | 默认只中文化用户可见内容，不改标识符 |
| 未给验证要求 | 默认只做结构级说明，不擅自写运行级结论 |
| 同时要建库又要跑复杂仿真 | 默认先收口最小闭环库结构与首个示例，再把仿真深挖交回父 skill / 领域 skill |

## 各任务类型的默认输出重点

### 从 0 到 1 建库

1. 顶层 package 结构
2. 正式库名方案
3. 第一阶段模型名单
4. `Examples` 与 `Tests` 的最小闭环入口

### 沿模板整理模型库

1. 模板与现状差异
2. 顶层分层保留项
3. 占位包替换方案
4. 公用层归位调整

### 扩展已有模型库

1. 可扩展位置
2. 新增业务包或子包建议
3. 对现有结构的影响
4. 最小验证范围

### 评审已有模型库

1. 保留项
2. 缺口
3. 错位项
4. 首批修补顺序

### 中文化修订

1. 需要中文化的范围
2. 应保留英文标识符的范围
3. 文档修订优先级
4. 潜在兼容性风险

### 图面与连线修复

1. 缺失的图面注解类型
2. 影响范围
3. 是否存在“仅有 `connect(...)`、未补 `annotation(Line(...))`”的连接
4. 修复顺序
5. 导图或图面复核要求

### 模型库 + 首个示例/测试验证

1. 最小闭环是否已经定型
2. 顶层库、首个 `Examples`、首个 `Tests` 的真实状态
3. 当前停留在结构级、检查级、翻译级还是运行级
4. 是否可以继续扩展更多业务包

## 分流后的下一步

- 任务类型明确后只选对应 workflow，按需读相关章节；模板方案仅在实际采用模板时加载，本地化与只读评审不进入完整建库链
- 若用户只要方案，停留在结构与执行路线层
- 若用户要真实落地，进入真实文件修改与阶段检查
- 若用户要求真实示例/测试验证，进入 `workflows/build-library-with-example-validation.md`，明确 load/check/translate/simulate/result 的请求终点；单说“首版模型库”不强制运行

## 完成标志

当以下三项都明确后，本文档的职责即完成：

1. 当前任务类型已识别
2. 缺失输入的默认补足策略已确定
3. 下一份应读取的 workflow / reference 已明确
