# 常见错误

## 目的

沉淀模型库开发中最常见的结构、文案、图面和交付错误，帮助优先排查真正影响交付的问题。

按具体问题读取，不作为强制全量检查链。以下固定公共层、接口本地移植、命名和顶层排序示例，仅适用于已采用 `template-package-scheme.md` 模板的任务；其他工程中的兼容原生接口或不同分层不因此成为错误。修复动作只在授权范围内执行，已有具体故障由父级调试入口主导。图面与真实验证遵循父级范围，案例说明不自动授权全库重构或仿真。

## 结构类错误

### 1. 占位包名直接进入交付

现象：

- 顶层或业务包还叫 `Components1`、`Components2`

处理：

1. 先按领域语义替换正式包名
2. 再调整对应 `Examples` / `Tests` / 文档中的引用

### 2. 公用层散落到业务包

现象：

- 连接器、类型、图标、常数、函数散落在 `Valves`、`Pumps` 等业务包中

处理：

1. 跨全库复用内容迁到 `Interfaces` 或 `Utilities`
2. 只保留业务包内部复用内容在各自 `Basics`

### 3. 通用函数长期内嵌在具体组件中

现象：

- 阀、泵、缸等具体模型内部声明了可复用函数
- 多个组件开始复制同一套局部函数

处理：

1. 把可复用函数迁到 `Utilities.Functions`
2. 组件中改为直接调用公用函数
3. 函数变多后按主题拆分 `Functions` 子包

### 4. 接口库没有建立通用接口与方向型接口分工

现象：

- 同一领域的端口都只用一个通用接口
- 入口、出口、正负端或 a / b 端没有区分
- 本该保留双向抽象的工作口也被强行写死方向

处理：

1. 先参考对应领域的 `Modelica` 标准接口库组织方式建立本地接口子包
2. 为确有方向语义的接口补齐 `_a` / `_b`、`_p` / `_n` 或其他等价方向型接口
3. 两接口元件优先使用成对命名的方向型端口
4. 方向不固定的工作口保留通用接口
5. 液压场景可进一步参考 `Modelica.Fluid.Interfaces`，例如补 `HydraulicPort_a` 和 `HydraulicPort_b`

### 5. 接口直接照抄标准库名称

现象：

- 本地接口类名与标准库 `Modelica` 中已有接口重名
- 用户无法快速区分“标准库原生接口”和“本地移植接口”

处理：

1. 标准库已有接口优先做本地别名或本地包装
2. 本地名称增加领域或语义前缀，例如 `FluidMediumPort_a`、`ThermalHeatPort_a`、`AnalogPin_p`
3. 自定义接口也避免直接照抄标准库已有类名；液压场景同样不要直接命名成 `FluidPort`

### 5.1 组件里直接使用了标准库接口

现象：

- 组件类中直接声明 `Modelica.*.Interfaces.*` 下的原生接口
- 本库明明已经有 `Interfaces` 子包，却绕过本地接口直接连到标准库

处理：

1. 先识别所需标准接口族
2. 将其移植或包装到当前模型库 `Interfaces` 下
3. 组件中统一改为使用本库接口，不再直接引用标准库原生接口

### 6. 把没用到的接口也预先移植进库

现象：

- 当前模型库只做少数几个领域，却提前把其他领域接口整包搬进来
- `Interfaces` 下出现大量当前版本根本没有组件引用的子包

处理：

1. 只保留当前组件实际会用到的接口子包
2. 未使用的标准接口等到对应组件出现时再移植
3. 优先保持接口库小而清晰

### 6.1 只移植了接口族中的单个成员

现象：

- 机械接口只包装了 `Flange_b`，却没有本地通用 `Flange` 和 `Flange_a`
- 液压或流体接口只迁了 `_a` 或 `_b` 中的一个
- 本地 `Interfaces` 中出现“能用，但接口族结构不完整”的半移植状态

处理：

1. 先识别当前组件实际落入的是哪个标准接口族
2. 补齐该族的无图标通用接口
3. 按当前组件的连接语义补齐 `_a` / `_b` 方向型接口；双向成组语义默认一起补齐
4. 再检查本地命名、图标继承和 `package.order`

### 6.2 自定义接口缺少默认实例化名称

现象：

- 在 Sysplorer 中拖放或实例化本地接口时，没有稳定的默认实例名
- 通用接口和方向型接口的默认实例名风格不一致

处理：

1. 给自定义接口或本地移植接口补 `defaultComponentName`
2. 通用接口优先使用通用名，例如 `port`、`flange`
3. 方向型接口优先使用 `port_a`、`port_b`、`flange_a`、`flange_b`
4. 再回看实例化后的显示效果和命名一致性

### 6.2.1 自建带图标接口未显示 `%name`

现象：

- `HydraulicPort_a`、`HydraulicPort_b` 这类自建方向型接口有图标，但实例化后名称不显示
- 端口已经有 `defaultComponentName`，但图标层仍看不到实例名

处理：

1. 在接口 `Icon(graphics = {...})` 中补 `Text(..., textString = "%name")`
2. 将名称放在图标主体外侧空白区，避免压住端口图形
3. 与 `defaultComponentName` 一起检查，保证默认实例名和显示名称一致

### 6.2.2 创建组件时接口没有在图形层实例化

现象：

- 组件在语义上依赖了接口类型，但图形层看不到实际接口实例
- 缺少 `Placement(...)` 或 `iconTransformation(...)`，端口无法正确落在图面边界

处理：

1. 在组件中以 connector 实例形式显式声明接口
2. 接口实例优先使用当前模型库 `Interfaces` 下的类型
3. 补齐 `Placement(...)` 与 `iconTransformation(...)`
4. 再检查图形层端口位置和连线可见性

### 6.3 接口库 partial 仍写成基础模型并绘制图标

现象：

- `Interfaces` 中的 partial 模型中文显示名仍写成“基础模型”
- 接口库基类带有矩形主体、名称文字或其他业务图标

处理：

1. 将接口库 partial 的中文显示名统一改为“基类模型”
2. 删除其 `Icon(...)` 注解，只保留接口位置、方向和文档说明
3. 让具体图标留在可实例化模型或业务包基类中

### 6.4 接口层未先收口就推进组件层

现象：

- `Interfaces` 目录已经建立，但 `package.mo`、`package.order`、接口类、partial 基类之间仍存在不一致
- 本地 connector 名称已经出现，例如 `BasicPin`，但在工具中无法稳定识别、继承或被组件引用
- `Interfaces` 中已有 partial 基类，同时 `Components/Basics` 中又补出一套语义接近的 partial，形成重复归口
- 为了先让元件能工作，先在组件层写 `PartialTwoPin`、源、传感器和无源元件，之后再回头修补接口层
- 首次 check 失败后，才暴露出 `within` / `package` / `end` 与目录不匹配、接口基类定义不稳、继承链断裂等问题

处理：

1. 先单独完成 `Interfaces` 层：校正每一级 `package.mo` 的 `package`、`end` 与真实目录一致，并确保不含 `within`
2. 在 `Interfaces` 子包内部先稳定接口族，再推进组件层；推荐顺序是“通用接口 -> 方向型接口 -> partial 基类 -> 组件引用”
3. 本地接口优先采用“标准库接口的本地包装或本地别名”路径，不要一开始就手写一套与标准语义平行的 `v` / `i` 实现
4. 接口层未稳定前，不要在 `Components/Basics`、`Sources`、`Sensors` 中复制第二套 partial 或 connector 语义
5. 请求真实检查时，先对受影响 `Interfaces` 做必要加载/check；文件任务以静态引用证据收口，不增加运行门槛

### 6. `Examples` 和 `Tests` 混放

现象：

- 用同一模型既当样例又当测试
- 测试模型散落在业务包下

处理：

1. 展示型入口放 `Examples`
2. 回归和验证入口放 `Tests`

## 中文化类错误

### 7. 只改标识符，不改说明

现象：

- 变量名改中文，但类说明、参数说明、文档说明仍是英文

处理：

1. 默认优先改用户可见文本
2. 只有用户明确要求，才评估是否改标识符

### 8. 中英混用无规则

现象：

- 一部分参数说明是中文，一部分是英文
- `UsersGuide` 和 `ReleaseNotes` 风格不一致

处理：

1. 先统一用户可见语言策略
2. 再做批量修订

## 图面类错误

### 9. 文本已连接，但图上没有连线

现象：

- 有 `connect(...)`，图上却没有线或线不可见
- 把 `connect(...)` 当成了图面已自动出线，交付的系统模型里看不到组件之间的连线

处理：

1. 先查 `annotation(Line(...))`
2. 再查 connector 实例的 `Placement(...)`
3. 再查 `Diagram(coordinateSystem(...))`
4. 明确补齐可见连线：`connect(...)` 只表示语义连接，交付的系统模型不能省略 `annotation(Line(...))`

### 10. connector 锚点异常

现象：

- 红色虚线、悬空端点、连线挂不到边界

处理：

1. 给 connector 实例补 `Placement(...)`
2. 同时补 `iconTransformation(...)`

### 11. 图标层接口和主体比例失衡

现象：

- 端口离主体过远或贴在主体内部
- 左右接口不对称，图标看起来歪斜
- 名称、参数文字压在图标主体或端口上

处理：

1. 参考 Modelica 标准库，把接口放到图标边界附近
2. 保持左右或上下对称，先调主体比例，再调端口位置
3. 把名称和关键标注移到主体外侧空白区

### 12. 图形层主链路和测量链混乱

现象：

- 主流路来回折返，设备前后顺序不清
- 控制链、测量链、机械链与液压链交叉缠绕
- 传感器离被测对象很远，靠长母线连接

处理：

1. 优先把主能量链排成一条清晰横向或纵向路径
2. 控制源放主链路上方或左侧，测点贴近被测对象
3. 机械负载、边界源、油箱等辅助对象放到主链路外圈
4. 优先使用短直、少拐点、正交的连线

## 交付类错误

### 13. 没有样例入口却宣称库可用

处理：

1. 已请求可用库且缺少所需示例时，补约定的 `Examples` 入口；骨架/文案任务不自动追加
2. 如果没有运行验证，明确写成“结构已整理，运行未验证”

### 14. 没有测试入口却宣称已闭环

处理：

1. 完整库闭环或明确测试请求缺少测试时，补约定的 `Tests` 或说明计划；仅示例请求不自动增加测试
2. 将“样例可展示”和“测试已闭环”分开表述

### 15. 把部分成功写成整体完成

现象：

- 只改了 package 文案，却把用户同时请求的结构和运行验收也写成已完成；纯文案请求可按其范围完成

处理：

1. 分开写明：结构、文案、验证、发布准备分别到了哪一步
2. 未做的部分单独列风险和下一步

### 16. 把开发阶段的执行顺序误写成顶层 `package.order` 顺序

现象：

- 因为开发时先收口 `Interfaces`、`Utilities`、`Sources`、`Sensors`，就把它们排到顶层 `package.order` 最前面
- 为了临时解决加载或依赖问题，在调试时把 `Interfaces` 放到 `UsersGuide`、`Examples` 和业务包之前
- 生成结束后仍保留调试阶段顺序，没有恢复到标准交付结构

处理：

1. 区分“执行顺序”和“交付顺序”：先收口公用层，不等于顶层展示顺序要把 `Interfaces` 放最前
2. 顶层 `package.order` 按标准架构回排为 `UsersGuide`、`Examples`、业务包、`Sensors`、`Sources`、`Interfaces`、`Utilities`、`Tests`
3. 不把 `package.order` 当成依赖修复工具；依赖问题应通过接口归口、引用修正和结构补全解决
4. 若调试时临时改过顺序，交付前必须按结构方案和 `workflow-checklist.md` 重新校正
