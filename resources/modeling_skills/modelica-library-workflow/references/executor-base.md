# 执行基线

## 职责与前提

本文件只规定库级任务的执行顺序。任务边界与 MCP 契约见 `shared-standards.md`，完成层级与最低证据见 `acceptance-checklist.md`，模板细则见 `template-package-scheme.md`。不得依据本地流程追加父级没有要求的验证或文档。

## 先确定终端阶段

| 本轮请求 | 本地执行终点 | 不自动追加 |
| --- | --- | --- |
| 方案、评审、命名建议 | 方案或评审结论 | 文件修改、加载、检查、仿真 |
| 生成骨架、修改文件、整理结构 | 文件落地及适用静态检查 | Sysplorer 启动、首个示例/测试运行 |
| 结构检查 | 请求对象的结构证据 | 全库运行验证 |
| 能加载 / check / translate | 对应指定阶段的真实证据 | 后续仿真与结果读取 |
| 可运行库、可运行示例、首版可用 | 约定示例/测试的真实运行证据 | 未要求的 KPI、曲线、动画、正式文档 |
| 结果分析或异常结果诊断 | 请求指标或故障所需取证 | 无关变量、额外工况、全库验证 |

“新建库”“首版模型库”“带示例/测试文件”本身不等于用户请求真实运行。用户未限定的必要静态检查可以完成，但不得用虚构的运行状态补齐表格。

## 按需执行顺序

1. 识别库级目标；普通单模型交回父级和相应领域。
2. 复用已确认的范围、依赖、版本和终端阶段，记录必要假设。
3. 只在创建或调整包结构时确定顶层 package、正式库名和首批交付粒度。
4. 采用模板时按其规则收口必要公共层；非模板项目保留现有兼容接口与分层。
5. 只落本轮需要的业务包、公共接口、Examples / Tests 或本地化修改。
6. 用 `workflow-checklist.md` 的相关章节做静态自检。
7. 需要真实验证时按父级工具契约执行到指定阶段；接口变更优先验证受影响接口和最小依赖，不默认扩大到全库。
8. 核对适用的 Gate 6，按实际证据提交完成层级。

## 骨架与首个可运行闭环

- 骨架任务可以只有 `package.mo`、必要 `package.order`、已请求的子包及入口占位；未包含可运行模型时，不因不能仿真判定骨架未完成。
- 完整首版可用库先稳定一个业务包及约定的首个 `Examples` / `Tests`，再扩展其他案例；针对只要求一个可运行示例的任务，不擅自再建并运行测试套件。
- 请求完整库闭环时，顶层加载/打开和首个示例、测试的检查、翻译、仿真分别记录；缺少任何已要求证据不能宣称整库运行通过。
- check、translate、simulate 是不同事实。只有实际仿真成功才可声明 `run-level-verified`；结果验收在 required 时额外核对指定变量及数据来源。

## 失败处理

已有具体故障按父级独立调试分流；新建中的失败保留原任务与已经成立的结构。复用父级分类重试规则，区分基础设施错误、同一修复假设和总体进展。没有新增证据时停止原策略并检查结构/接口/入口，不重新从建库第一步开始，也不通过增加验证范围寻找“通过”。
