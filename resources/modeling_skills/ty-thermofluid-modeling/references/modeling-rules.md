# 建模与排错规则

本文用于整理热流体与空气处理建模时的结构规则、排错优先级与最小可执行策略。

## 目录

- `通用动作规则`：明确执行动作必须走 MCP / Sysplorer 官方工具。
- `版本与加载提示`：记录版本依赖和环境边界。
- `介质确认优先级`：在落模前先确认介质假设。
- `热流体系统结构规则`：处理阻容组织和离散管道选择。
- `编译优先的边界补齐策略`：当拓扑未闭合或端口悬空时，先补最小边界。
- `空气处理系统结构规则`：处理气体成分和组件适配性。
- `模型库依赖绑定规则`：交付为模型库时必须绑定依赖库。
- `模型文件书写规则`：约束包文件和单位别名写法。
- `建模顺序建议`：统一开环优先和分段验证路径。
- `常见报错与排查方向`：缩短定位问题的路径。
- `相关引用`：把图面、交付和验收要求下沉到专用参考文件。

## 通用动作规则

- 本文件的开环、闭环和分阶段策略不扩大父级确认的验收范围。文件交付、只读评审或 Documentation-only 本身不授权启动软件或检查原件；离线/仅静态任务只做适用静态检查。用户明确请求实时只读查询时，按父级会话契约仅执行授权查询，不据此自动 check 原件、翻译、仿真或改模。实时检查、翻译、仿真及结果读取仍须属于本次请求及其写回授权范围。
- 会话连接、模型管理、检查、翻译、仿真、结果读取与绘图，优先使用 MCP / Sysplorer 官方工具。
- 是否成功以工具实际返回为准，不凭主观判断补写“已完成”。
- 如果会话异常、工具失败或环境阻塞，应明确说明阻塞点，不伪造成果。

## 版本与加载提示

- `TYThermoFluidSys` 与 `TYAirTreatmentAndVentilation` 手册都依赖 `Modelica 4.0.0.TY.1` 和 `TYMedia V1.4.0`。
- `TYAirTreatmentAndVentilation` 手册提到依赖 `MWORKS.Sysplorer 2025a` 及以上版本。
- `TYThermoFluidSys` 手册提到 `Sysplorer 2024a` 以上版本支持介质传递功能。
- 若当前环境版本更高，以实际可连接、可加载的版本为准。

## 介质确认优先级

- 系统构建前优先确认介质类型，再决定组件与子库。
- 至少确认以下适用信息：
  - 是水、蒸汽、制冷剂、空气、湿空气、油液还是乙二醇等混合介质。
  - 是单相还是两相。
  - 是否允许或预期发生相变。
  - 是否可压缩。
  - 是否需要水蒸气、`CO2` 或其他混合组分。
  - 是否有浓度、配比或表格介质要求。
- 若这些信息未明确，不要过早锁定两相换热器、单相管道、湿空气处理器或特定制冷剂组件。
- 若为了先搭可运行骨架必须作假设，应显式记录当前假设，并在交付时提醒用户确认。

## 热流体系统结构规则

### 阻容连接规则

- 两个以上阻性件相连时，中间通常增加容性件。
- 两个以上容性件相连时，中间通常增加阻性件。
- 目标是减少系统非线性、提高求解效率并降低振荡风险。

### 管道离散方式

- `TYThermoFluidSys` 管道边界存在 `V-F`、`F-V`、`F-F`、`V-V` 等多种离散方式。
- 不只看拓扑连通，还要判断离散方式是否与上下游组件性质匹配。
- 对液体单相主回路，如需体现沿程压降、温升、换热分布，或系统已出现明显非线性偏差、振荡、初始化困难，默认优先用均相离散管道，例如 `TYThermoFluidSys.Pipelines.DistributePipe_Homogeneous`。
- `LumpPipe` 更适合作为极简骨架、快速占位或对分布特性不敏感的验证模型，不应默认替代受热段、换热段或测试段。
- 选离散管道后，应显式判断上下游组件偏阻性还是偏容性，再决定 `frictionDistribution`。
- 常用判断方法：
  - 上游是阀、孔口、局部阻力、泵流阻端等偏阻性组件，下游是换热器容积、容腔、容器、边界容积等偏容性组件时，优先用 `VolFric`。
  - 上游是容器、边界容积、容腔等偏容性组件，下游是阀、孔口、局部阻力等偏阻性组件时，优先用 `FricVol`。
  - 上下游两侧都明显偏阻性时，再考虑 `FricFric`。
  - 上下游两侧都明显偏容性时，再考虑 `VolVol`。
- 若无法快速判断，先把上下游组件按“阻性件 / 容性件”写成一行映射，再选 `frictionDistribution`，不要跳过这一步。
- 只要显式设置了 `frictionDistribution`，交付时应说明当前选择与上下游组件关系。

## 编译优先的边界补齐策略

- 若系统图来自工艺草图、PFD 或不完整拓扑，默认先接受“开式等效”首版，不强求第一次就闭成真实回路。
- 只要存在以下任一情况，优先补边界组件再继续：
  - 流体主链路两端没有明确连接对象。
  - 为了先验证泵、阀、换热器、容腔或主管段，需要给回路提供稳定入口 / 出口参考。
  - 直接闭环后 `check`、`translate` 或初始化明显更难定位。
- 液体单相主回路的首选做法：
  - 在入口侧补 `TYThermoFluidSys.Boundaries.BoundaryPressure` 或等效压力边界。
  - 在出口侧补 `TYThermoFluidSys.Boundaries.BoundaryPressure` 或等效压力边界。
  - 泵若需要转速输入，补 `BoundarySpeed`。
  - 热源或冷源暂时没有真实设备时，补 `BoundaryHeatFlow` 或其他热边界做等效。
- 补边界的目标是让系统先具备可检查、可翻译、可做首轮短时仿真的最小条件，而不是伪装成最终工艺闭环。
- 边界补齐后，交付中必须说明：
  - 哪些边界是为首版验证临时加入的。
  - 它们分别等效哪类真实设备或外部系统。
  - 后续准备如何替换回真实回流、用户边界或完整设备模型。
- 若当前任务目标只是“先让系统编译成功”，优先补最小边界，不同时引入复杂控制器、完整闭环回流和额外二次设备。

## 空气处理系统结构规则

- 空气处理组件先校核介质成分，而不是只看端口是否可连。
- 湿度相关部件必须有水蒸气。
- `CO2` 去除相关部件必须包含 `CO2` 组分。
- 风机、压缩机、换热器的介质范围应与所选工质匹配。

## 模型库依赖绑定规则

- 若交付物是系统模型库而不是单个散落的 `.mo` 文件，顶层必须提供 `package.mo` 和 `package.order`。
- 顶层 `package.mo` 应直接写正式包名，不包含 `within`，并通过 `annotation(uses(...))` 绑定依赖库。
- `uses(...)` 中只保留真实依赖：
  - 使用热流体系统库时，通常至少绑定 `Modelica`、`TYThermoFluidSys`；若调用 `TYMedia` 介质则同时绑定 `TYMedia`。
  - 使用空气处理库时，通常绑定 `Modelica`、`TYAirTreatmentAndVentilation`；若调用 `TYMedia` 介质则同时绑定 `TYMedia`。
  - 若系统同时使用两个专业库，则两个专业库都写入 `uses(...)`。
- 依赖版本优先与项目约定或手册一致；若当前环境中已确认可用版本，应按实际版本填写。
- 不要把“当前会话里恰好已加载”的库当作隐式前提。
- 单个模型或一次性测试台可按请求保留单文件形式交付、复用或迁移，并在适用位置声明实际依赖；这些动作本身不要求新增模型库。仅当用户要求库级组织，或任务确实涉及包结构、公共接口、Examples/Tests 组织等库级范围时，才追加模型库工作流并维护包文件。

## 模型文件书写规则

- 顶层模型库 `package.mo` 默认包含：
  - `package 正式包名`
  - `extends Modelica.Icons.Package;`
  - `annotation(uses(...));`
- 若案例需要使用 `Modelica.Units.SI` 简写，使用 `import SI = Modelica.Units.SI;`。
- 不要在案例模型里写 `package SI = Modelica.Units.SI;` 作为单位别名。
- 测试案例和模型产物默认写入 Agent CWD；用户已明确指定产物路径时使用该路径。不得以 Skill 所在目录或其同级目录作为默认输出位置。

## 建模顺序建议

1. 先确定系统边界与目标工况。
2. 先做组件映射，再做拓扑。
3. 优先先搭开环主链路，再补闭环回路。
4. 先确认介质与相态，再定主回路。
5. 再补边界、传感器与控制器。
6. 先选介质，再批量检查组件兼容性。
7. 先做适用的领域静态校核，再按本次请求执行所需的 `CheckModel`、翻译或仿真。

### 先开环后闭环

- 默认先建立可独立调试的开环系统，再演化为闭环系统。
- 热流体系统优先采用“入口边界 -> 泵 / 阀 / 主管段 -> 受热段或负载 -> 散热段 -> 出口边界”的开环骨架。
- 空气处理系统优先采用“入口边界 -> 风机 / 处理段 -> 负载或房间等效段 -> 出口边界”的开环骨架。
- 若系统图本身没有给出完整回流路径，或当前闭环还不稳定，先补入口 / 出口边界把主链路撑起来，再逐步回填真实回流支路。
- 开环阶段优先校核组件映射、介质兼容性和连接组织；仅结果验收在范围内时核验关键变量可读性。
- 开环阶段按请求完成所需证据：文件任务完成静态检查；要求 check 时取得检查证据；要求翻译或仿真时才继续对应阶段。描述动态行为本身不授权仿真，check-only 不追加翻译或仿真。
- 开环完成本次所需阶段的校核后，再按已授权的闭环目标把出口边界替换为回收箱、蓄能箱、回液管路、回风支路、三通混合段或其他闭环组件。
- 闭环改造时一次只增加一类回路要素，每次增加后只复核受影响且属于本次请求的阶段；文件任务不因此启动软件，check-only 不增加仿真，结果仅按请求读取。

## 常见报错与排查方向

### 热流体系统卡滞、除零、`NaN`

- 手册给出的典型原因包括阀类组件孔径过小、流量过大、管道直径或长度不合理。
- 优先处理方式：
  - 减小系统流量。
  - 增大孔口直径。
  - 调整管径、长度。
  - 若当前是闭环系统，先退回开环骨架验证，再逐段加回回流、旁通或容积组件。

### 空气处理系统算不动或结果异常

- 优先排查：
  - 介质成分是否满足组件要求。
  - 湿空气模型是否真的包含水蒸气。
  - `CO2` 净化任务是否真的使用了含 `CO2` 的混合气体。
  - 是否误用了错误的单组分介质。
