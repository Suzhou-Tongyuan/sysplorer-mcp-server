# 七门闸验证工作流

仅在当前任务需要实时 Sysplorer 操作时，会话与工具探测才是前置条件，不属于门禁；MCP 0.4 分类、starting/错误/重试和自动布局副作用统一见 `references/shared-standards.md`。开始实时操作前，发现可用工具/API 签名；在支持时探测并健康检查 Sysplorer 会话，且不得干扰用户已附着的 GUI 会话。纯计划、骨架/文件、离线日志和文档任务不因此自动启动软件。产物使用 Agent CWD 和显式路径；不得调用 `ClearAll` 或 `ChangeDirectory`。

## Gate 1：范围与授权

确定目标、用户意图、验收条件、交付物、请求的验证深度和成功观测量。仅计划型请求在计划后停止；用户已明确要求搭建、执行、检查、翻译或仿真时，该请求本身即为对应范围的执行授权，不再要求二次确认。只有缺少会实质改变方案的关键选择时才请求用户决策。评审、文档修改或只读查询必须保持原有限定范围，不得擅自扩展为建模或仿真。

## Gate 2：证据与组件边界

选择拓扑或写入连接前，必须依据公开证据确认所选类、端口、参数、连接器、单位和商业库边界。

- 按 `references/domain-routing-and-library-versions.md` 保留有效实现边界；未指定时标准库满足则使用，不足时保留标准库并以商业组件补足，记录功能缺口、接口依据、版本来源及子系统责任。
- 所有商业类均按受保护依赖处理；仅使用文档、已登记语料、公开内省和必要的最小黑盒验证，不得检查受保护源码。
- 确认每个 `connect(...)` 端点及连接器兼容性；混合边界还要确认暴露 `Inport` / `Outport` 的类型和维度。
- 记录选用和拒绝的方案、假设及剩余证据缺口；不得虚构名称或签名。

## Gate 3：构建

以正确的建模形式创建或修改请求的模型，并保持项目元数据一致。

- Modelica 物理拓扑使用 `.mo` 文本；普通 Sysblock 拓扑归属官方 API 与专业 Skill。
- 新建 Modelica 类保持 package、文件和类名一致；顶层及子 package 的 `package.mo` 不写 `within`，普通类 `.mo` 文件的 `within` 与所属 package 路径一致；适用时更新直接父目录的 `package.order`。
- 在不清楚的拓扑继续扩展前，遵循对应 Modelica、混合和领域工作流，先完成最小且可评审的模型。
- 保留后续 Gate 6 所需的足够图形注解；不得将可见 Line 误当作有效 `connect(...)` 方程。

## Gate 4：检查

按 Gate 1 的验收范围和 Gate 5 的验证深度，仅在请求需要实时检查时，对最新修改对象运行适用检查，通常为 check_model。骨架/文件交付只做适用静态检查；只读和 Documentation-only 遵守无越界写回约束。需要实时检查的混合模型按 Sysblock 子模型、可独立检查 plant、混合顶层顺序执行。检查失败按已授权范围处理；已知检查失败不得继续依赖它的翻译或仿真。

检查成功只证明相应模型检查通过，不证明布局验收、翻译、仿真、结果可读、KPI 达标或用户目标完成。检查可自动布局无 Placement 的用户文件；调用前按 shared-standards 判断写入授权，调用后检查 preflight_steps 和实际文件改动。只读任务不因需要诊断就授权修改原件。

## Gate 5：验证设计

按请求结果选择验证深度，而不是对所有工作强制仿真。

| 请求结果 | 最低要求 |
|---|---|
| 计划、评审、文档或不改变行为的修改 | 用户要求的证据，以及验证该修改所需的检查 |
| 影响行为的组件修改 | 验证模型、受影响检查和用户验收要求的行为证据；不得据此自动读取结果 |
| 新系统，且验收止于检查、翻译和仿真成功 | 测试台、检查、翻译、仿真；结果验证为 `not_required` |
| 完整行为、KPI 或结果交付 | 测试台、翻译、仿真、用户要求的实际结果访问和目标 KPI 证据 |

仿真任务应定义测试台、求解器/时间范围和负责的模型。只有用户要求结果或 KPI 核验时，才定义预期观测量、结果变量与 KPI/验收阈值；不得硬编码结果文件路径，必须使用实际结果上下文和 `result_manager`。

### 结果验证适用性

- 用户明确要求结果数值、KPI、曲线或动画，或验收条件明确依赖结果时，结果验证为 `required`，只读取验收所需内容。
- 用户未提出上述要求时，结果验证必须标记为 `not_required`，不得调用 `result_manager`，不得自动查看曲线或动画。“行为证据”本身不构成结果读取授权。
- 若终止条件为 check + translate + simulate 成功，取得三项成功证据后停止运行/结果链；若适用 Gate 6 尚未完成，只补该图面验收、必要图形修复后的检查与交付记录，不追加 KPI、结果或新的仿真。

## Gate 6：完整布局与图面验收

每个本次新建或实际修改的图形对象都执行 Full Gate 6，并在最终图形交付前完成。Gate 6 可以在翻译或仿真之后完成；纯视觉布局缺陷不阻止翻译或仿真，也不否定已经取得的检查、翻译或仿真事实。只有模型检查发现的图形注解语法或结构错误才阻止后续执行。

1. 只列出本次新建或实际修改的图形目标，类型可为 `system`、`subsystem` 或 `component`。未修改的继承对象、标准库内部图形和未触及层级不展开验收。
2. Documentation-only、纯代码且没有图形对象、只读任务或没有改变任何图形目标的修改，将 Gate 6 标记为 `not_required`；不再要求证明整个继承树没有组件实例。
3. 对新建或修改的系统/子系统，检查关键实例可见、关键连接可见、连接锚点基本对应，以及 Icon/Diagram 可读。
4. 对新建或修改且需要图形交付的组件，检查外部连接器的 `Placement` / `iconTransformation`、关键内部实例、计划可见的 `Line` 和 Icon/Diagram 可读性。未修改组件不做组件级展开。
5. 首次图面验收不额外主动调用 `smart_layout`；Full Gate 6 失败且修复必要时才显式调用 writeback_mo 并给出目标类与文件。MCP 检查/翻译/仿真的内部自动布局可能更早写回，须记录实际变更，不能宣称首次检查绝不改图，也不能把自动布局成功当作验收通过。
6. 只有工具实际写回 `.mo` 时才重新执行 Gate 4，并把布局动作和复检结果写入 `repairs`。确认仅改变图形注解且复检通过时，不重复翻译或仿真；若同时改变行为文本，则重做受影响的后续 Gate。
7. Sysblock 图面由其归属专业 Skill 执行；混合任务中，各专业 Skill 检查自己负责的变更层，本 Skill 只汇总 Sysblock 子模型、物理层和混合顶层的状态，不重复执行相同图面检查。
8. 结构化证据是共同基础：记录目标、实例/端口位置、关键连接与锚点、可读性检查及实际证据来源。图片按用户需求和工具能力补充，不全面禁图，也不凭结构数据虚构目视结论；用户明确要求图片时，导出/查看失败必须记录缺口而非静默跳过。
9. 仅记录 `layout.status`、`layout.level`、`layout.targets`、`layout.checks` 和 `layout.evidence`。Gate 6 失败只阻止完整图形交付，不把已成功的翻译或仿真改判为失败。

## Gate 7：交付证据

分别报告检查、布局、翻译、仿真、结果验证、修复和剩余缺口。各验证项统一使用 `required`、`not_required`、`passed`、`failed` 或 `blocked`；`required` 用于执行前的待办状态，最终交付时应落为其余四种状态之一。最小记录结构如下：

```json
{
  "target_status": "met | not_met | blocked",
  "check": {"status": "passed", "errors": []},
  "layout": {
    "status": "passed | not_required | failed | blocked",
    "level": "full",
    "targets": ["ChangedModel"],
    "checks": ["instances_visible", "key_connections_visible", "diagram_readable"],
    "evidence": []
  },
  "translation": {"status": "passed"},
  "simulation": {"status": "passed"},
  "result_verification": {"status": "not_required", "evidence": []},
  "repairs": [],
  "remaining_gaps": []
}
```

仅当请求的验收条件确实满足时，才能将 `target_status` 标记为 `met`。不得由检查成功推断翻译成功，由翻译成功推断仿真成功，或由仿真完成推断结果验证成功；但结果验证为 `not_required` 时，不得把缺少结果读取作为交付阻塞项。Gate 6 失败只使完整图形交付未达标，不覆盖已成立的翻译或仿真状态。证据不完整时，必须准确标记 `not_met` 或 `blocked`。

## 修复闭环与终止条件

任一 Gate 失败时，确定失败 Gate 和最近一次有效输入，收集明确的错误、检查、翻译、仿真、KPI 或布局证据，并将原因归类为：需求、库选择、类/端口缺失、连接器/类型/维度、参数/单位、初始化/事件、包元数据、图形注解、工具/环境或验收失败。

1. 只修复已明确的局部原因，然后重做受影响 Gate 及被该修改影响的全部后续 Gate。
2. 按 `references/shared-standards.md` 分别记录基础设施重试、同一修复假设与整体推进；停止无改善的假设，必要时隔离最小案例取证，再从失败 Gate 恢复，不在本工作流另设次数政策。
3. 不得为了取得工具通过而删除用户要求的组件、拓扑或 KPI；需要实质性重新设计时请求用户决策。
4. 只有在“已用 Gate 7 证据满足目标”“用户要求停止”或“存在需要用户输入或外部状态改变的明确硬阻塞”时，流程才可结束。终点为 check + translate + simulate 时，三项成功后停止运行/结果链；只收完适用 Gate 6、必要图形复检与交付证据，然后结束，不追加额外运行或结果任务。

应使用最短的有效检查、翻译、仿真、完整图面验收和按需结果读取序列。Gate 6 可以在翻译或仿真之后完成，但必须在最终图形交付前完成；首次验收不主动追加布局调用，但 MCP 内部可能自动写回，须按实际副作用记录。未要求结果时，不得追加 KPI 读取、曲线或动画。
