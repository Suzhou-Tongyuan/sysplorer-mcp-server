# Modelica 建模工作流

当分流结果为 Modelica 物理建模、商业 Modelica 组件或 Modelica 库工作时使用本工作流。Modelica 拓扑必须使用 `.mo` 文本。仅任务涉及库级包结构、公共接口、Examples/Tests 组织、本地化或模型库评审时，在完成路径判断后追加 `modelica-library-workflow`；单模型及单个测试台不自动追加；不得用本工作流重建普通 Sysblock 拓扑。

## 1. 范围、授权与验收

1. 明确目标模型或包、物理领域、所需行为、库边界、交付物、观测量、验收条件和验证深度。
2. 仅计划型请求在搭建计划后停止。用户已明确要求搭建、执行、检查、翻译或仿真时，该请求本身视为对应范围的执行授权；只有缺少会实质改变方案的关键选择时才请求用户决策。
3. 对评审、文档或不改变行为的修改，保持用户指定的只读或有限范围；不得仅因存在工作流就自行创建测试台或仿真。
4. 按 `references/domain-routing-and-library-versions.md` 复用实现边界；未指定时标准库满足则使用，不足时保留可用标准库并补充商业组件，记录缺口和接口证据。

## 2. 在建立拓扑前取得证据

1. 写入 `connect(...)` 前，依据当前公开证据确认每个选定类、连接器、公开端口、参数、单位及连接兼容性。
2. 对商业类，只能使用 `get_lib_model_document`、公开文档、已登记语料、公开内省，以及必要时的最小黑盒检查；不得读取、解密、反编译、解包、解析或提取受保护商业类的源码文本。
3. 选择负责主要组件边界的领域 Skill；只有存在真实跨领域组件边界时才追加其他领域 Skill。
4. 对未解决的证据缺口必须如实说明，不得虚构类、端口、参数或连接器。

## 3. 包与文件完整性

创建或修改 Modelica 包、类时，执行以下规则：

- 根目录名、顶层 `package` 名、文件名和类名必须在大小写和层次上保持一致。顶层和所有子 package 的 `package.mo` 均不得包含 `within` 子句；普通类 `.mo` 文件使用 `within` 时，其路径必须与所属 package 一致。
- 每个 package 目录都必须有 `package.mo`。直接子项写入相邻的 `package.order`，每行只写一个类名或子包名，不含路径和扩展名。
- 新建直接子类或子包后，必须更新其父目录的 `package.order`；不得用私有排序注解替代。
- 在顶层 `package.mo` 的 `uses(...)` 中声明外部依赖。版本按 `references/domain-routing-and-library-versions.md`：车辆/商业路径固定 `Modelica(version = "4.0.0.TY.1")`；仅主规则单独使用时允许用户/工程有效版本覆盖。
- `package`、`model`、`block`、`connector`、`record`、`function` 等类声明的描述字符串属于类头，字符串后不得添加分号；类体中的声明、方程、算法语句和注解仍按各自语法使用分号。
- 需要资源时使用规范的 `Resources/` 目录；不得把互不相关的核心类压入同一个 `.mo` 文件。
- 新建 Modelica 组件或模型的英文类名必须只使用 ASCII 字母和数字且不超过 15 个字符；类声明中的中文简短描述不得超过 20 个可见字符。用户或项目已有明确规范时以其为准，不为满足本规则重命名现有类；`.mo` 文件名和 `package.order` 条目必须与类名同步。

## 4. 编写 Modelica 文本

1. 使用表达物理含义的名称：类使用 `PascalCase`；参数、变量和连接器实例使用描述性的 `camelCase`；避免 `x1`、`tmp` 等无意义名称和魔法数字。
2. 物理量优先使用 `Modelica.Units.SI` 类型。关键参数应包含单位、默认值和简短物理说明；无量纲量也应显式说明。
3. 连续物理关系优先写入 `equation`；仅离散或程序式逻辑使用 `algorithm`。保持声明、方程/算法和注解的顺序清晰。
4. 适用时使用标准物理连接器，只连接兼容端口。`connect(...)` 定义方程以及守恒/相等关系，改变其端点属于行为修改。
5. 初始化会影响行为时，必须使用 `initial equation` 或显式的 `start` / `fixed` 设置。事件逻辑应集中于 `when` / `elsewhen`，使用 `noEvent()` 时说明理由。
6. 公开类应有简短说明；描述字符串后不得添加分号。记录不显然的物理假设、适用参数范围和已验证工况，而非重复代码字面内容。
7. 将可复用共性提取为 `partial model` / `extends` 或无状态 `function`。测试工况应放在测试台或系统模型层，不得隐藏在可复用组件内。
8. 不得遗留无意的孤立组件实例；重要物理组件不得完全依赖默认参数而不显式给出任务所需的关键物理设置。

## 5. 生成可审查的图形信息

创建或修复图形化 Modelica 模型前，读取 `references/modelica-diagram-connect-semantics.md` 和 `references/modelica-style-guide.md`。

- 将 `connect(...)` 视为模型结构/方程，将 `Placement(...)` 视为实例几何，将 `annotation(Line(...))` 视为可见走线。Line 注解不能替代有效的 `connect(...)`。
- 对图标层可见的外部连接器给出可用的 `Placement` 和 `iconTransformation`；对关键内部实例给出可读的 `Placement`；使计划可见的连接能通过 `Line` 注解或等效的已接受布局表示审查。
- 初始摆放和走线应对齐真实连接器锚点。固定 20×20 尺寸、网格间距、`%name` 和非默认参数显示属于项目约定或风险检查，而非通用门禁；以项目约定或已评审的布局工具结果为准。
- 图形交付的 Gate 6 时序、通过条件和结构化证据以 `workflows/seven-gates-validation.md` 为唯一权威。首次验收不主动追加 `smart_layout`；显式修复条件与 MCP 内部自动布局的授权、写回记录及复检均按该权威工作流处理。

## 6. Modelica 局部检查与诊断

1. 创建或修改模型文本后先做适用静态检查；只有本次验收范围需要实时模型检查时，才使用已发现的适用工具（通常为 check_model）。骨架/文件、只读和 Documentation-only 任务不因此自动启动软件或检查原件；按 shared-standards 核对写回副作用。
2. 检查通过仅证明当前模型通过编译/结构检查，不证明图面验收、翻译、仿真、KPI 或用户目标已完成。
3. 仅修复已有明确证据的局部原因：连接器不兼容、类/端口证据缺失、参数或单位错误、初始化/事件问题、包元数据错误，或图形写回导致的变化。
4. 失败分类和重试按 `references/shared-standards.md`；停止无改善的同一假设，隔离最小案例取证，再从七门闸的受影响阶段恢复。
5. 不得为了通过检查而删除用户要求的拓扑、组件或 KPI；需要实质性重新设计时必须请求用户决策。

## 7. 请求验证并提供 Modelica 证据

按 `workflows/seven-gates-validation.md` 的 Gate 5 选择验证深度，Gate 6 验收实际变更图形对象，Gate 7 记录各阶段独立事实和最终状态；不另立完成层级或重复维护验收表。

只有请求需要时才翻译、仿真和读取结果。验收止于 check/translate/simulate 时 verify_result_var 留空，不追加结果、KPI、曲线或动画；用户要求结果或异常结果诊断时取得必要证据。调用和结果来源规则见 `references/shared-standards.md`。完成适用图面交付、达到请求终点即停止。
