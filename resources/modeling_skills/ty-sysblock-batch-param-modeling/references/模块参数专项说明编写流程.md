# 模块参数专项说明编写流程

本文档用于沉淀后续补充定制模块参数说明时的统一流程。目标不是描述某一个模块，而是给后续 AI 生成模块参数专项说明时提供可复用规则。

## 1. 适用范围

适用于以下任务：

- 新增某个模块的参数专项说明
- 根据新的参数对话框截图或 JSON 参数，补充已有专项说明
- 调整字段口径，例如把某些字段明确为参考字段、可写字段、或内部处理字段

不适用于以下任务：

- 一般接口说明重写
- 测试用例设计本身
- Sysblock 拓扑建模或仿真流程

## 2. 输入材料清单

生成模块参数专项说明前，至少收集以下材料：

- 模块参数对话框截图
- 对应模块的 JSON 参数样例
- 当前技能下已有的模块参数专项说明样例
- `references/模块参数对象映射说明.md`

如果未提供模块对应截图和 JSON 参数，不要直接生成专项说明。应优先要求用户补充：

- 模块参数对话框截图
- 对应模块的 JSON 参数样例

如果用户暂时无法提供这两项，至少要求提供其他可参考资料，例如：

- 参数对话框文字说明
- 帮助文档
- 相关测试材料
- 接口返回样例
- 现有模块说明中可明确类比的资料

目的不是补齐形式，而是提升参数说明准确性，避免把未确认字段硬写成规则。

注意：

- 这些材料只用于生成和校验结论。
- 最终输出到“模块参数专项说明”文档中的内容，只保留结论信息，不写参考材料来源痕迹。
- 不要在专项说明文档中写出类似“根据某截图”“根据某 JSON”“参考某材料”这类表述。
- 专项说明文档应直接写“已确认字段”“输入规则”“修改建议”等结论。

如果同一模块有多张截图，应优先覆盖：

- 主参数对话框
- 影响字段解释的下拉数据或特殊控件截图

## 3. 核心判断顺序

编写时按以下顺序判断，不要跳步：

1. 判断该模块完整读取返回 `dict` 还是 DataClass
2. 判断界面中哪些字段是主要修改字段
3. 判断哪些字段只是参考字段
4. 判断哪些字段已经内部处理，不需要在文档里体现
5. 判断是否存在简化输入规则
6. 判断是否存在字段联动或顺序敏感行为

## 4. 字段分类规则

### 4.1 主要修改字段

满足以下任一条件时，可作为主要修改字段写入文档：

- 字段直接对应参数对话框中用户可编辑项
- 字段是后续 `SetModelParamValues` 的主要回写目标
- 字段改变会直接影响模块可见行为

### 4.2 参考字段

满足以下任一条件时，应明确标注为参考字段：

- 字段只用于展示候选项或来源列表
- 字段用于帮助理解底层函数、总线、信号、参数来源
- 字段通常不应作为主动修改目标

当前已确认的典型例子：

- `BusSelector.AvailableSignals`
  - 参考字段，表示左侧可选信号列表，不是修改字段
- `CCaller.AvailableFunctions`
  - 参考字段，表示当前 C 文件内可选的 C 函数列表
- `CCaller.Arguments[].CName`
  - 参考字段，表示 C 侧原始参数名

- `From.AvailableTags`
  - 参考字段，表示可选的Goto标签候选列表，只读，回写被拦截

### 4.3 内部处理字段

如果字段已经被内部处理，不希望调用者或测试人员关注，则不要在专项说明文档中体现。

当前已确认例子：

- `BusCreator.BusTypeIsAuto`
- `BusCreator.BusTypeName`

对这类字段：

- 不要在字段映射表中写出
- 不要在修改建议中暴露
- 不要在测试注意点中要求单独验证

## 5. 简化输入规则提炼方法

如果截图或实际数据表明某字段支持简化输入，应单独列出“输入规则”章节。

优先关注以下情况：

- 下拉值有完整展示形式，但用户可用简化值输入
- 某些类型名、枚举名、总线类型名可以直接输入
- 某些后端字符串支持缩写，内部会自动补全

当前已确认例子：

- `BusCreator.OutDataTypeStr`
  - `auto` 等价于 `"inherit: auto"`
  - `Bus1` 可作为总线类型名简化输入
  - 同时支持全量输入 `"inherit: auto"`、`"Bus: Bus1"`

如果没有明确证据，不要擅自补充简化输入规则。

## 6. 文档输出结构

每个模块的专项说明建议固定采用以下结构：

1. 模块名称与用途
2. 适用场景
3. 已确认字段与对话框映射
4. 参考字段说明
5. 简化输入规则
6. 推荐 AI 调用方式
7. 修改建议
8. 最小校验示例
9. 测试注意点

说明：

- 不是每个模块都必须有“参考字段说明”
- 不是每个模块都必须有“简化输入规则”
- 如果某部分不适用，可以省略，不要为了凑结构硬写

## 7. 编写要求

- 只写当前材料能确认的内容，不要脑补
- 只输出结论信息，不输出参考材料信息
- 界面字段名、JSON key、说明口径三者要一致
- 明确区分“主要修改字段”“参考字段”“内部处理字段”
- 如果字段顺序有意义，要在说明里点出
- 如果字段联动明显，要在修改建议和测试注意点里点出
- 示例代码优先采用“完整读取 -> 局部修改 -> 整体回写”
- 不要在专项说明正文里写“根据某截图”“根据某 JSON”“参考某资料”等来源性话术

## 8. 同步更新要求

新增或更新模块专项说明后，同步做两件事：

1. 更新 `references/模块参数对象映射说明.md`
2. 如该模块规则已经稳定，可回收进 `SKILL.md` 的模块说明或流程规则中

## 9. 后续 AI 生成时的引用方式

后续 AI 在补充新模块参数说明时，优先按以下流程执行：

1. 读取本流程文档
2. 检查该模块对应截图和 JSON 参数是否齐备
3. 若材料不齐，先要求用户提供截图、JSON 参数或其他可参考资料
4. 读取该模块对应截图和 JSON 参数
5. 对照现有专项说明样例，判断字段分类
6. 生成单模块专项说明文档
7. 同步更新 `模块参数对象映射说明.md`
8. 如提炼出稳定共性规则，再补回 `SKILL.md`
